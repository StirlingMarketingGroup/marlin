# 0001: Mount remotes through one portable core and a thin adapter per OS

**Status:** accepted
**Date:** 2026-11-11
**Issue:** #369 (epic #368)

## Decision

Marlin mounts each remote account as a native folder. Seven choices make that up.

1. **Marlin owns the layer between providers and the OS.** A new crate, `marlin-vfs`, defines Marlin's virtual filesystem (VFS): the operations that every provider and every OS adapter share.
   - A **node ID** names one file or folder for the life of a mount. An **open-file handle** names one open instance of a file.
   - Adapters call the core with node IDs and handles: look up a name, get attributes, list a folder, open, read a byte range, release, and later create, write, flush, rename, and delete.
   - The core calls each provider through one async trait, keyed by the provider's own item ID (a Drive file ID, an SFTP path).
   - The core owns everything in between: the node table, name rules, caches, time limits, and the **write spool** (local files that hold edits until the remote confirms them).
   - No type from FUSE or WinFsp crosses into the core or a provider.
2. **One thin adapter per OS.** Each one translates between the core and one kernel interface, and does nothing else.

   | OS      | Kernel side                                    | Rust side                                                         | The user installs                                           |
   | ------- | ---------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------- |
   | Linux   | FUSE, in the kernel                            | `fuser`, no libfuse; it runs `fusermount3`                        | the `fuse3` package                                         |
   | macOS   | macFUSE 5, FSKit backend (no kernel extension) | Marlin's own bindings to the low-level API of macFUSE's libfuse 3 | macFUSE, by themselves, and two switches in System Settings |
   | Windows | WinFsp 2, native API (not its FUSE layer)      | Marlin's own bindings to the WinFsp DLL                           | WinFsp                                                      |

3. **Mounts live in one helper process, `marlin-mount`.** It is a separate binary under `src-tauri/crates/`, shipped beside the app the way `marlin-smb` is. One process per user serves every mount. The app starts it on demand and detached, so it outlives a hot reload, an app crash, and every window. When the user quits Marlin, the app asks the helper to finish pending uploads, unmount everything, and exit. The helper links the provider code. The app stops talking to remotes itself and reads them as ordinary paths.
4. **The app controls the helper over a local socket.** There is one endpoint per user: a Unix domain socket on Linux and macOS, a named pipe on Windows, open to that user only. The protocol is JSON-RPC 2.0, one JSON object per line, the same framing `marlin-smb` uses. It carries control messages only: mount, unmount, list, status, and events such as "sign-in expired". File contents never cross it. Secrets never cross it; each side reads the OS keychain. The first message in each direction carries a protocol version. An app that meets a helper with a different version asks it to unmount and exit, then starts its own. A second helper never takes over live mounts.
5. **Mounts get stable names under one folder.** Each account mounts at `~/Marlin/<provider>-<account>`, for example `~/Marlin/gdrive-ana@example.com` or `~/Marlin/sftp-deploy@build.example.com`. On Windows the folder is `%USERPROFILE%\Marlin` and each mount is a directory mount, not a drive letter. The name is built once from the account's full identity (for SFTP: user, host, and a port other than 22), with characters the OS cannot hold replaced. It is then stored with the account, so it is the same on every launch. If two accounts would get the same name, ignoring letter case, the later one gets a number on the end. The helper creates the folder when it mounts and removes it when it unmounts, so nothing can write into a dead mount point by mistake. It never mounts over a folder that already has something in it.
6. **A slow provider call never blocks the rest of a mount.** The FUSE adapters hand each kernel request to a tokio task and return. The task answers the kernel when the provider call finishes. WinFsp allows a late answer only for read, write, and list-folder calls, so the Windows adapter does the same for those three. Its other callbacks (open, get attributes, rename) wait on a dispatcher thread, outside the tokio workers, and hold no mount-wide lock while they wait. The core caps the calls in flight per mount and puts a time limit on each one. A call that runs out of time fails with an I/O error. It never hangs the mount. A mount is reported to the app only once the OS shows it.
7. **Linux is the tested reference, and writes move earlier.** The first Google Drive slice (#372) is built and tested on Linux, where a container can run it with no install. The macOS adapter follows at once. Write-back (#376) moves ahead of the Windows adapter (#375) and the migration (#377). See "What follows".

## Why

**The problem.** The provider trait has no way to read or write file contents, so every copy between two backends is hand-written per pair of providers. [Location providers](../location-providers.md) lists the eight places where that breaks. A native mount removes the pairs: the OS, Finder, Explorer, and every other app see a folder.

**No shared Rust layer exists.** No maintained Rust crate puts one API over both FUSE and WinFsp. `fuser` speaks the FUSE kernel protocol. It does nothing on Windows, and the macOS spike showed it cannot drive the one macFUSE backend that needs no kernel extension. WinFsp has a FUSE-compatible layer, but its project recommends the native API for new filesystems. So the portable API has to be Marlin's own, and it has to be small enough that each adapter stays thin.

**The helper must not die with the UI.** `npm run tauri dev` restarts the app on every Rust change. A mount served from the app process would vanish each time. A mount belongs to the process that serves it, not to the process that started it, so a detached helper keeps mounts alive.

**Callbacks block the OS.** A kernel request holds the calling app (Finder, a shell) until the filesystem answers. A provider call can take seconds. If the answer came from the dispatch thread, one slow download would freeze every other file in the mount.

## Evidence

### Spikes

The spike is `spikes/mount-hello/`. It mounts a read-only filesystem with two files. A read of `slow.txt` is answered three seconds later, to stand in for a slow network call.

| Platform | What ran                                                                                                                                                              | Result                                      |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| Linux    | `run-linux.sh`: the Rust program on `fuser` 0.18.0, in a Debian 12 container, kernel 7.0.14, `fuse3` 3.14.0, as a non-root user                                       | **Passed**, 2026-11-11                      |
| macOS    | `run-macos.sh`: `macos-hello.c` on the low-level API of macFUSE 5.5.0's libfuse 3.18.3, FSKit backend, macOS 27.2 on Apple Silicon                                    | **Passed**, 2026-11-11                      |
| macOS    | The Rust program on `fuser` 0.18.0, same machine, FSKit backend                                                                                                       | **Failed**: `fuser` cannot use this backend |
| Windows  | The Rust program in `windows/` on WinFsp 2.1.25156 through its own bindings, Windows 11 on ARM64 (Insider build 26300.9711), as an administrator and as a normal user | **Passed**, 2026-11-11                      |

What the Linux run showed:

- **Mount, list, read, unmount** all passed for a non-root user. The mount went through the setuid `fusermount3`. The binary links no libfuse.
- **Slow calls do not block fast ones.** While the 3-second read was waiting, a folder listing and a file read finished in about 1 ms, and 4 other callbacks reached the filesystem. Every `fuser` reply type the spike uses can move to another thread, so choice 6 works on Linux as written.
- **A killed helper leaves a dead mount.** After `kill -9`, the mount stays in `/proc/mounts` and every access fails with "Transport endpoint is not connected" until something runs `fusermount3 -u`. So the helper must sweep `~/Marlin` for dead mounts when it starts.
- **A clean signal unmounts.** `SIGTERM` unmounted and exited 0. `fuser`'s `BackgroundSession::join()` waits and does not unmount; the helper must call `umount_and_join()`.

**Not covered on Linux:** the container was given `/dev/fuse`, `CAP_SYS_ADMIN`, and no AppArmor profile. A bare Linux desktop, Flatpak, Snap, and AppImage are untested.

What the macOS runs showed:

- **Mount, list, read, unmount** all passed at a path under the home folder, with no kernel extension, no Recovery Mode, and no restart.
- **Slow calls do not block fast ones.** The filesystem answered the slow read from another thread three seconds later. A listing, a read, and a lookup of a new name finished while it waited, on a single session-loop thread. A one-off timing of the listing and the read gave 5.6 ms. The program logs each callback that arrives during the slow read, and the script requires at least one, so the OS cache alone cannot pass this step.
- **`fuser` cannot use the FSKit backend.** `fuser` needs a file descriptor that speaks the FUSE wire protocol. With `backend=fskit`, macFUSE's `fuse_mount_compat25` returns -1 and `fuse_chan_fd` returns -1: there is no such descriptor. Only libfuse's own session loop can serve the mount. `fuser` reported this as "Unspecified Error". These three results came from one-off test programs that are not in this branch.
- **Two switches, not one.** macFUSE installs two file system extensions, "macFUSE" and "macFUSE (local)". With only the first one on, the mount fails with `File system extension io.macfuse.app.fsmodule.macfuse-local not enabled`.
- **The kernel backend is a trap.** Each mount attempt without `backend=fskit` made macOS ask the user to shut down and change security settings in Recovery Mode. Marlin must always pass `backend=fskit` and never fall back.
- **The mount appears late.** The volume shows up one to three seconds after `fuse_session_mount` returns. The helper must wait until the mount point is a mount before it tells the app.
- **A killed helper leaves a dead mount, and it is easy to clear.** After `kill -9` the mount stays in the mount table and every read fails at once with "Device not configured". Nothing hangs. A plain `umount` by the same user clears it.

**Not covered on macOS:** Finder, Spotlight, writes, speed, Intel Macs, any macOS before 27, and the kernel backend. The spike is C. The Rust bindings are not written (risk 1).

What the Windows runs showed:

- **Marlin's own bindings work.** The program has no WinFsp files at build time. It finds the install folder in the registry and loads `winfsp-a64.dll` at run time. Before WinFsp was installed, an earlier build of the program started and printed "WinFsp is not installed". The program in the repo keeps that code, but it was not run again without WinFsp.
- **WinFsp installs quietly.** `msiexec /i winfsp-2.1.25156.msi /qn /norestart` installed the driver from an administrator session with no restart.
- **Mount, list, read, unmount** all passed at a directory mount under the user folder, both elevated and as a normal process in the desktop session.
- **The adapter must refuse writes itself.** Creating a file failed with `ERROR_WRITE_PROTECT` because the spike's create callback returns that status. WinFsp's `ReadOnlyVolume` flag only labels the volume. In the WinFsp 2.1 source the driver uses the flag for the volume's attributes and for nothing else, so every write call still reaches the filesystem. The spike refuses a create and an overwrite, and leaves the other write callbacks out. On the mount, a new file and an overwrite failed with "The media is write protected", and a rename failed with "Incorrect function". `del hello.txt` printed no error and the file stayed: with no delete callback, WinFsp reports success and deletes nothing.
- **A slow read does not block fast calls.** The read callback returned `STATUS_PENDING`, and a tokio task sent the answer later with `FspFileSystemSendResponse`. With one dispatcher thread, a listing and a read finished in about 2 ms while the slow read waited, and 21 callbacks arrived in that time. This covers reads only. WinFsp has no late answer for open, get attributes, or rename, and a slow one of those was not tested.
- **One read by an app can be several read calls, and one can start at the end of the file.** `fs::read_to_string` on the 5-byte slow file made three read calls: 4,096 bytes at offset 0, 32 bytes at offset 0, and 32 bytes at offset 5. Each waited three seconds, so the app waited nine. The spike turns WinFsp's cache of file information off, and this was not tried with it on. The adapter must answer a read at the end of a file without a provider call.
- **A killed helper leaves nothing behind.** After `taskkill /F` the mount directory was gone, and the same path mounted again at once. This is better than the WinFsp FAQ promises.
- **An elevated process cannot open a normal user's mount.** A mount made by a normal process could not be read from an administrator session: "The path cannot be traversed because it contains an untrusted mount point" (error 448). Windows does not trust a directory mount point that a non-administrator created.
- **Zero timestamps break `dir`.** The spike sends no file times, and `dir` printed "The parameter is incorrect" for each file. The adapter must always send real times.

**Not covered on Windows:** x64, a release build of Windows (the VM runs an Insider build), Explorer, Windows Search, writes, and a drive-letter mount.

## What a mount promises on every OS

This is the smallest set that all three adapters can keep. A provider may do better. Nothing may do worse.

| Topic               | Promise                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity            | A node ID stays the same for the life of a mount and is never reused in that mount. It is not promised across mounts.                                                                                                                                                                                                                                                                                                                     |
| Names               | Case-sensitive, kept as the remote spells them. Names in one folder are unique: the core adds a suffix when the remote has duplicates (Google Drive allows them) and escapes characters the OS cannot hold. Case-sensitive names are untested on macOS and Windows, where apps expect the opposite.                                                                                                                                       |
| Reads               | Any byte range, in any order, with bounded memory. Nothing downloads a whole file to serve a small read.                                                                                                                                                                                                                                                                                                                                  |
| Writes (#376)       | A file's new contents reach the remote when the last writer closes it. Writes at any offset work, through the write spool. If the upload fails, the spool is kept and the user is told: an edit is never dropped silently. No promise is made about what the remote shows while the file is open. Issue #376 decides what `fsync` waits for, how a conflict with a changed remote file resolves, and how a spool survives a helper crash. |
| Rename              | Atomic inside one mount when the provider can do it. A rename across two mounts fails with a "cross-device" error. The calling app then has to copy the item and delete the source after the copy succeeds. Finder and Explorer do that. Marlin's own move code calls `fs::rename` directly today, so #377 must give it the same fallback.                                                                                                |
| Timestamps          | Modified time from the remote, to the whole second at least. Access and change times repeat the modified time.                                                                                                                                                                                                                                                                                                                            |
| Permissions         | Made up: the mounting user owns everything, with fixed modes. Changing owner or mode succeeds and does nothing, so `cp -p` and Finder do not fail. Only the mounting user can open a mount. Linux gets this by not passing `allow_other`. Windows gets one fixed security descriptor that names the user and the system. This is untested on macOS and Windows: #373 and #375 must each try a mount from a second user account.           |
| Links               | No hard links. No new symbolic links.                                                                                                                                                                                                                                                                                                                                                                                                     |
| Locks               | Not sent to the remote. Two machines can open the same file.                                                                                                                                                                                                                                                                                                                                                                              |
| Extended attributes | None. On macOS the adapter refuses `._` files and `.DS_Store`, so Finder leaves none on the remote. macFUSE has mount options for this (`noappledouble`, `noapplexattr`), but the FSKit backend may not honor them.                                                                                                                                                                                                                       |
| Errors              | The core has one error type. Each adapter maps it to an `errno` or an `NTSTATUS`: not found, read-only, no space, sign-in needed, timed out, offline, not supported.                                                                                                                                                                                                                                                                      |
| Change notices      | None from the remote. OS caches expire after a short time. Marlin's refresh drops the core's caches, and the adapter drops the OS's caches where the OS allows it. macFUSE's FSKit backend does not support that yet, so on macOS a refresh shows up when the OS cache expires.                                                                                                                                                           |

How each OS differs underneath:

| Topic                    | Linux (FUSE)                             | macOS (macFUSE)                        | Windows (WinFsp)                                                                |
| ------------------------ | ---------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------- |
| Lookup model             | Node IDs with lookup and forget counts   | The same model, through libfuse        | Paths; the adapter walks them through the core's lookup                         |
| Local default for names  | Case-sensitive                           | Case-insensitive; apps may assume it   | Case-insensitive; reserved names such as `CON`, 260-character paths in old apps |

## Packaging, upgrade, and uninstall

- **The helper.** `marlin-mount` ships as a Tauri `externalBin`, signed and notarized with the app.
- **Linux.** The `.deb` declares `Depends: fuse3` and the `.rpm` declares `Requires: fuse3`. An AppImage cannot declare anything, so the helper checks for `fusermount3` and Marlin shows the install command when it is missing. Upgrades and removal are the package manager's job.
- **macOS.** Marlin does not ship or download macFUSE. It checks for `/Library/Filesystems/macfuse.fs` and its version, then sends the user to <https://macfuse.github.io>. Mounts need macOS 15.4 or later. Marlin cannot read the state of the two switches, so it tries the mount and, when macFUSE answers "File system extension not enabled", shows where both switches are. macFUSE updates and uninstalls itself. Removing Marlin leaves macFUSE alone. The helper needs its own entitlements file with `com.apple.security.cs.disable-library-validation`, because a hardened-runtime binary may not load a library signed by another team, and macFUSE's library is. The app already carries the same entitlement for the SMB library (issue #157). This is untested: the spike is not signed.
- **Windows.** Marlin checks the registry for WinFsp and sends the user to <https://winfsp.dev>. The helper loads the WinFsp DLL at run time from the install folder in the registry, so the helper starts and can report "WinFsp is missing" when it is not there. WinFsp's license lets an open-source app ship the unmodified installer. Marlin does that only after risk 4 is closed.
- **Leaving nothing behind.** The helper unmounts everything when the user quits Marlin (choice 3). On start, it removes dead mounts and empty folders under `~/Marlin`.

## Rejected

- **Apple File Provider and the Windows Cloud Files API.** These are what Google Drive and OneDrive use, and they need no driver. They are sync engines, not mounts. Items are addressed by ID, files are copied to the local disk when opened, and the system asks for the whole file when an app clones it or reads it through file coordination. Cloud Files only projects a folder on an NTFS disk, and Microsoft's own pages disagree on whether an app outside MSIX may use it. Each would be a second architecture with a Swift or C++ extension, and Linux would still need FUSE.
- **Apple FSKit, used directly.** No third-party install, which makes it the likely long-term macOS adapter. Today it needs a Swift app extension, a URL-backed volume needs macOS 26, Apple does not say whether an app outside the App Store may ship one, and Apple's own engineers call its read and write speed "not great". The adapter boundary keeps this door open.
- **FUSE-T.** No kernel extension, but its license requires a paid license for "commercial use" without saying what that means, and it serves files over loopback NFS, which has the gaps below.
- **A loopback NFS or WebDAV server**, mounted by the OS's own client, as `rclone nfsmount` does. It needs no install on macOS. NFS has no open or close, so the helper cannot know when a written file is complete. Any local process can connect to the port. On Linux the mount needs root. On Windows, WebDAV caps file size and the NFS client is not always present. rclone still labels its NFS mount experimental.
- **One libfuse-style API on every OS**, with WinFsp's FUSE layer on Windows (what rclone does through cgofuse). There is no maintained Rust equivalent of cgofuse, `fuser` cannot sit on WinFsp, and WinFsp recommends its native API.
- **The `winfsp` crate.** It is GPL-3.0 and does not carry WinFsp's exception. Linking it would put the whole helper under GPL terms. Marlin writes its own bindings to avoid that.
- **Dokany.** LGPL on the parts an app links, a slower release pace than WinFsp, an open kernel-crash report, and a Rust crate last released in 2022.
- **Windows Projected File System.** An optional Windows feature that an administrator must turn on, and Microsoft says it is for fast local stores.
- **`fuser` on macOS.** It cannot drive macFUSE's FSKit backend (see Evidence). It could only use the kernel backend.
- **macFUSE's kernel backend.** It needs a kernel extension, which on Apple Silicon means a trip to Recovery Mode to lower the security level.
- **One libfuse 3 adapter for both Linux and macOS.** One binding would serve both, and Linux tests would cover the macOS code. But Linux would trade a pure-Rust crate for unsafe bindings and a libfuse link, and the two libraries differ: Debian 12 ships `libfuse3.so.3` (3.14) and macFUSE ships `libfuse3.4.dylib` (3.18). Revisit this if the two adapters drift apart.
- **The `fuse3` crate.** Its API is async, which fits, but it documents no macOS support and lists unfinished parts. `fuser` with replies moved to tasks gives the same result, and the spike proved it.
- **Linking libfuse on Linux.** `fuser` does not need it, and skipping it removes a build dependency and an LGPL question.
- **Serving mounts from the app process.** Every hot reload and every app crash would drop all mounts.
- **One helper process per mount.** It isolates a crash to one mount, but the app would have to find and supervise many detached processes after a restart. Time limits in the core handle the common failure, a hung provider. Revisit this only if real crash data calls for it.
- **Drive letters on Windows.** There are 26, other software takes them, and a letter is not a stable name for an account.
- **A hidden mount folder**, such as `/run/user/<uid>` on Linux. Other apps' file dialogs cannot find it, and reaching other apps is the point of the epic.

## What follows

**Order of work.** Write-back is what makes dragging a file onto a remote work, and it shapes the core's handle and flush design, so it cannot wait until eighth.

1. #370: the `marlin-vfs` core, tested with an in-memory provider and no kernel.
2. #371: the `marlin-mount` helper, its socket, and the dead-mount sweep.
3. #374: the Linux adapter, on `fuser`. It goes first because a container can test it.
4. #372: Google Drive, read-only, as the first real provider, on Linux. Issue #463 (Drive tokens in a plain-text file) lands before or with it, because the helper reads those tokens.
5. #373: the macOS adapter, on Marlin's own libfuse 3 bindings, checked in Finder with the Drive provider. It uses the same node-ID model as the Linux adapter, so the two share their translation code.
6. #376: write-back.
7. #377: move Marlin's own navigation and file operations to mounted paths.
8. #375: the Windows adapter, after #473 is closed and Marlin has a Windows build (#135). No workflow builds or tests Marlin on Windows today, so the adapter cannot ship before the app does.
9. #378: hardening and packaging.

**Easier after this.** A new provider implements one trait and gets copy, paste, drag and drop, open, and thumbnails for free. The provider-pair table in `paste_items_to_location` goes away.

**Harder after this.** macOS and Windows users must install a third-party driver before remotes work, and macOS users must also flip two switches. Marlin has to explain those steps well, and it has to keep working, with remotes turned off, when the driver is missing. Two of the three adapters are hand-written bindings to C libraries. On the tested Windows build, an administrator process could not open a directory mount that a normal process made.
