# Testing

Marlin has static checks and fourteen test suites. CI runs the static checks, the unit tests, the end-to-end tests, the real-app tests on Linux, and the Rust tests that need no mount, remote server, or account (the SFTP tests start their own `sshd`). It does not run the real-app tests on macOS, the tests that mount for real, or the tests that need samba, a remote server, or an account, so run those yourself when you change that code.

**Covers:** `package.json` (the test scripts), `vitest.config.ts`, `src/test-setup.ts`, `playwright.config.ts`, `e2e/`, `vitest.app.config.ts`, `app-tests/`, `.github/workflows/check.yml`, `.husky/pre-push`, `src-tauri/tests/`, `src-tauri/crates/marlin-smb/tests/`, `src-tauri/crates/marlin-smb/test-in-docker.sh`, `src-tauri/crates/marlin-smb-client/`, `src-tauri/crates/marlin-vfs/tests/`, `src-tauri/crates/marlin-gdrive/tests/`, `src-tauri/crates/marlin-sftp/`, `src-tauri/crates/marlin-test-keychain/`, `src-tauri/crates/marlin-test-samba/`, `src-tauri/crates/marlin-mount/tests/`, `src-tauri/crates/marlin-mount/test-sweep.sh`, `src-tauri/crates/marlin-fuse/tests/`, `src-tauri/crates/marlin-fuse/test-in-docker.sh`, `src-tauri/crates/marlin-fuse/test-on-mac.sh`
**Checked against the code:** 2026-11-23

## The suites

| SFTP                 | `npm run test:rust`                      | `cargo test`                                                    | yes        | a Rust toolchain; `sshd`                              |
| SMB client           | `npm run test:rust`                      | `cargo test`                                                    | yes        | a Rust toolchain; `procps` on Linux                   |
| Mount helper         | `npm run test:rust`                      | `cargo test`                                                    | yes        | a Rust toolchain; `procps` on Linux                   |

`npm run check` treats Rust warnings as errors. The pre-push hook runs it, so a push fails on a lint, format, type, or Rust warning.

CI also runs `npm run check:licenses`, which is not part of `npm run check`: see [Licenses](licenses.md#the-check).

CI skips a job's steps when the files they cover did not change (`check.yml` uses path filters). The Rust tests have a narrower filter than the static checks: see [Rust tests](#rust-tests).

**Each runner keeps its own Rust build folder,** `~/.cache/cargo-target/<runner name>/marlin-check`, so Cargo rebuilds only the crates that changed. The `lint-typecheck-rust` job builds everything there. It is per runner, not per machine, for two reasons. Cargo judges a workspace crate fresh by file times, so a folder shared by two checkouts can hand one PR's build of a crate to another PR. And a runner runs one job at a time, so no other job can relink the app between its build and its tests. The job deletes the folder at its start when it holds more than 25 GB, because old builds pile up with each toolchain or dependency change. Every Rust build in `check.yml` runs with `RUSTFLAGS=-D warnings`, so the real-app test build reuses most of the crates the Rust tests compiled. It also runs with `CARGO_PROFILE_DEV_DEBUG=line-tables-only`: the builds take a fraction of the disk of full debug info, and a backtrace (`RUST_BACKTRACE=1`) still names file and line.

## Unit tests

- They live in `src/__tests__/unit/` (store, hooks, utils), in `src/components/__tests__/`, and beside the code as `*.test.ts` (`*.test.mjs` in `scripts/`).
- `src/test-setup.ts` mocks `@tauri-apps/api/core` and `@tauri-apps/plugin-dialog`. A test sets what `invoke` returns.
- Most of the weight is on `useAppStore`: navigation, per-folder preferences, the hidden-files toggle, and the filter.

## End-to-end tests

- They live in `e2e/`, one `*.spec.ts` per area.
- **They do not run the desktop app.** Playwright starts `npm run dev` and opens the frontend in Chromium. `e2e/tauri-mocks.ts` is injected before page load and fakes every Tauri command with an in-memory file tree.
- So these tests cover the React UI and the store. They cannot catch a bug in Rust or in a real OS integration. The [real-app tests](#real-app-tests) can.
- **The port is 1420 unless `E2E_PORT` is set.** `playwright.config.ts` reads it for both the server and the base URL. In CI, the `e2e-tests` job asks the system for a free port and sets `E2E_PORT` to it: the runners are separate processes on one host and share its ports, so two runs on a fixed port collide.
- Locally, Playwright reuses a server already on that port. In CI it starts a fresh one, uses one worker, and retries a failed test twice.
- A new backend command that the UI calls on load needs a fake in `tauri-mocks.ts`, or the page fails in every spec.

## Real-app tests

These start the real app and drive its window: click, type, read the page, take a screenshot. [Decision 0004](decisions/0004-real-app-tests.md) says why they work this way.

- **Run them with `npm run test:app`.** It builds a test build of the app, then runs every `app-tests/*.test.ts` with Vitest. To run one file, add its path: `npm run test:app -- app-tests/directory-watcher.test.ts`.
- **The test build** is a debug build with the Cargo feature `app-test`, in its own folder, `src-tauri/target/app-test/`. The feature serves WebDriver on a local port, keeps secrets in memory, not in the OS keychain, and on macOS copies files to a pasteboard of its own. It does not compile in a release build. The first build takes a few minutes and about 8 GB. Later runs take seconds to build.
- **It runs beside `npm run tauri dev`.** It never touches `src-tauri/target/debug/`. Its window opens on screen but does not take the keyboard.
- **Each test file starts its own app** with `startApp()` from `app-tests/app.ts`, and stops it in `afterAll`. The app gets a temporary home folder and temp folder, and sees only a short list of environment variables. So it starts with default settings and no accounts, and it cannot read or change yours. `startApp()` returns once the app has opened its first folder. It returns `browser` (a WebdriverIO client), `files` (an empty folder to put test files in), `home` (the app's temporary home folder), and `stop`. `runCommand(browser, command, args)` in the same file calls one Tauri command in the page and returns its value, or its error text when it fails.
- **`app.ts` also has the steps most tests share.** `openFolder(browser, folder)` types the folder into the path bar and returns once the app watches it: a change made before that is never reported. `fileRow(browser, name)` finds a file's row, `rowNames(browser)` lists the names the view shows, `sizeBytes(browser)` and `sizeTitle(browser)` read the size from the status bar, and `showView(browser, view)` switches to grid or list view with the app's shortcut. `commandOrControl` is the modifier of the app's shortcuts: Cmd on macOS, Ctrl elsewhere.
- **A failed test saves a screenshot** of the window it was on, to `test-results/app/<file>--<test>.png`, and prints the path. An app that starts but never opens its first folder saves `<file>--startup.png`. Each run of the suite first empties `test-results/app/`, and `npm run test:e2e` empties all of `test-results/`, so look before you run either again. Under `test-in-docker.sh` the printed path starts with `/work/`, and the file lands in `test-results/app/` of your checkout. In CI, the "Upload real-app test screenshots" step keeps them for 7 days as the `app-test-screenshots` artifact of the run.
- **`sftp.test.ts` starts OpenSSH's `sshd` as the user, on a free local port, with key sign-in only.** The key has a passphrase, so the app's keychain read is part of the test. It calls the app's SFTP commands with `browser.execute`, not through the UI, because it checks the backend's half of the flow. The commands add a server, trust its host key, list a folder, read a file, and remove the server. The test needs `/usr/sbin/sshd`. A Mac has it. CI and `test-in-docker.sh` install `openssh-server`.
- **The clipboard is the test build's own on macOS.** The `app-test` feature copies files to a pasteboard named for the app's process, so a test never replaces what you copied, and two runs at once never share one. On Linux the app uses the display's clipboard through the `xclip` command: Xvfb's own under CI and `test-in-docker.sh`, which install `xclip`, but your desktop's when you run the suite on a Linux desktop. A copy finishes after its key returns, so a test that pastes first waits until `clipboard_get_contents` holds its own file.
- **On macOS the Trash is the real one.** A file the app moves to the Trash lands in your own `~/.Trash`, not under the temporary home. `file-operations.test.ts` names its file with a random ID and removes it from `~/.Trash` at the end. On Linux the Trash is under the temporary home.
- **A test acts like a user.** It finds elements by `data-testid` and the `data-*` attributes on a file row, as the end-to-end tests do. `await browser.saveScreenshot('/tmp/shot.png')` saves a picture of the window. `browser.execute` runs a script in the page; use it to wait for app state that has no sign on screen, not to skip the UI.
- **Clicks and keys are page events.** The server clicks with the element's `click()` and then `focus()`: no mouse-down, and focus does not leave a text field for an element that cannot take it. A key is a `KeyboardEvent` with its modifiers set, sent to the focused element. So a key reaches every shortcut the page handles itself (`src/App.tsx`), and none that only the native menu has. Pressing Enter in the path bar moves focus to the files, so the file shortcuts work right after `openFolder`. A click on an `<option>` does not change its `<select>`: use another control, as `preferences-window.test.ts` does with the theme buttons.
- **`browser.$` fails when its selector matches more than one element** (WebdriverIO 10's strict mode). Use `browser.$$`, or a selector that matches one. The list view's column headers repeat the status bar's labels, so `sizeTitle` looks for a `Size` span whose parent has a `title`.
- **Read many elements in one `browser.execute` script,** as `rowNames` does. `browser.$$(...).map(...)` sends one request per element, all at once. On Linux, such a burst for about 30 rows crashes the test build with `malloc(): unaligned tcache chunk detected` (#655). Read text in a page script or from an attribute, too: on Linux, `getText` on the status bar's `//div[@title][span[text()="Size"]]/span[2]` returns the whole segment ("Size6.2 MiB"), where macOS returns the span's own text.
- **A wait for a changed file needs a long timeout on macOS. A wait for a new, renamed, or removed one does not.** On a busy Mac, the event for changed bytes in an existing file can come minutes late. An added, removed, or renamed entry shows in about a second (see "A watched folder on macOS has two sources" in [Architecture](architecture.md)). `directory-watcher.test.ts` waits 10 seconds for each change. On Linux every event comes at once.
- **To run it on Linux from a Mac, use `app-tests/test-in-docker.sh`.** It runs the same command in a container with a virtual display. Use it to look into a Linux failure from CI, or to see Linux behavior before you push.
- **What it cannot reach:** the app menu, the native context menu, a drag out of the window, and system dialogs. WebDriver sees the page only. A test that mounts an account is also out for now: the mount helper is its own process and uses the real keychain (#580). Other windows it can reach: each window's handle is its Tauri label (`main`, `preferences`), so `browser.switchWindow('preferences')` moves to Preferences.
- **What the suite covers:**

  | File                         | What it checks                                                                                                                                                                                                                                                                   | Runs on      |
  | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
  | `directory-watcher.test.ts`  | A file written under a temporary name and then renamed shows its final name with no refresh (#194).                                                                                                                                                                              | macOS, Linux |
  | `file-view.test.ts`          | A folder of 500 files shows every file once, in list view and in grid view. The view never scrolls sideways (#480): a grid follows the window's width after its folder empties and fills, a narrow list fits, and files that come and go neither widen it nor leave a row faded. | macOS, Linux |
  | `file-operations.test.ts`    | A new folder takes the name typed into it. A rename and a move to the Trash each come back with undo. A copied file pastes into another folder.                                                                                                                                  | macOS, Linux |
  | `preferences-window.test.ts` | A theme picked in the Preferences window changes the file browser and is saved.                                                                                                                                                                                                  | macOS, Linux |
  | `growing-file.test.ts`       | While a file is written without a pause, the list still refreshes, and it shows the final size once the writing stops (#194).                                                                                                                                                    | Linux        |
  | `delete.test.ts`             | A permanent delete removes a folder and a broken link, and does not follow a link inside the folder.                                                                                                                                                                             | macOS, Linux |
  | `archive-extract.test.ts`    | A refused "Extract Here" leaves the folder as it was.                                                                                                                                                                                                                            | macOS, Linux |
  | `sftp.test.ts`               | The SFTP commands against a local `sshd`: add a server, trust its host key, list a folder, read a file, remove the server.                                                                                                                                                       | macOS, Linux |

  `growing-file.test.ts` does not run on macOS: there the file events for a file written through one open handle come only when it is created and closed, so the list does not change while the file grows.

- **CI runs it on Linux,** as the "Run real-app tests" step of the `lint-typecheck-rust` job in `check.yml`, under Xvfb (`xvfb-run -a`). It runs when the job's `check` path filter matches and the steps before it pass. A failing test fails the job, and the step stops after 30 minutes. It points `src-tauri/target/app-test` at the runner's build folder (see above), so the build stays warm. It builds with `-D warnings`. `npm run check` never compiles the code behind the `app-test` feature, so this step is the one check that fails on a warning there. To see such a failure on your machine, run `RUSTFLAGS="-D warnings" npm run test:app`: `test-in-docker.sh` builds without that flag. Cargo keeps a second copy of every crate for the new flags, so this run is a cold build.
- **It is a step of the one job that installs Rust.** All runners on a machine share one `~/.cargo`. Two jobs of one run that both install the toolchain can do so in the same second on one machine, and one of them then fails with "Text file busy" (#648). So every step that needs Rust goes in `lint-typecheck-rust`.
- **CI does not run it on macOS.** No Mac is among the self-hosted runners, and a GitHub-hosted Mac starts empty, so every run would be a cold build of about 8 GB. On a busy Mac an event for changed bytes can also come minutes late (see the bullet on waits above), which would make a CI check flaky. Run it on a Mac yourself when a change can only be seen in the running app (`AGENTS.md`, "Before you call work done").

**An agent checks its own work with this suite.** When a change can only be seen in the running app, write a test for it in `app-tests/`, run it, and keep the test in the branch. For a one-off look, write a throwaway test that saves a screenshot, read the picture, and delete the test.

## Rust tests

- **`npm run test:rust` runs the Rust tests that need no mount, server, or account**, with warnings as errors. It runs `cargo test` for the app, then for every workspace crate but `marlin-smb`. A test marked `#[ignore]` does not run.
- **CI runs `npm run test:rust` on Linux** when a file under `src-tauri/` or `check.yml` changes (the `rust` path filter in `check.yml`). So CI runs the unit tests of the Linux half of `marlin-fuse`, which a Mac compiles out, and runs the helper's tests against that half. It never compiles the macOS half. It also never compiles the kqueue watch in `src-tauri/src/fs_watcher.rs` or runs its test, so run `npm run test:rust` on a Mac when you change that file. It does not run the tests that mount: they are marked `#[ignore]`.
- **A test that calls `zpl_rs` holds `RENDER_LOCK`** from `thumbnails/generators/zpl.rs`, as the generator does. Two renders at once abort the whole test process. See [Thumbnails](thumbnails.md#limits).
- Unit tests sit in `#[cfg(test)]` modules inside the source files, mostly in `locations/` and `thumbnails/`.
- **The Windows tests of `src-tauri/src/delete_entry.rs` run only on Windows**, and CI does not run them: they cover junctions and the read-only flag. Run `cargo test --lib delete_entry` in `src-tauri/` on Windows when you change that file or the version of `remove_dir_all`.
- The RAR tests read the files in `src-tauri/tests/fixtures/rar/`. UnRAR can read an archive but cannot write one, so no test can build its own. Rebuild them with the `rar` tool (`brew install rar`). For `sample.rar`, write `top level` to `notes.txt` and `inside folder` to `folder/inner.txt`, each with one line feed at the end, then run `rar a -r sample.rar notes.txt folder`. For `volumes.part1.rar` and `volumes.part2.rar`, one archive in two volumes, write the line `0123456789` 200 times to `data.txt`, then run `rar a -m0 -v2k volumes.rar data.txt`. The RAR tests do not compile on Windows, where Marlin has no RAR reader (see [Location providers](location-providers.md)).
- `cargo test -p marlin-vfs` runs the mount core's tests. A plain `cargo test` does not include them. They run on an in-memory provider and need nothing installed. See [Mount core](mount-core.md).
- `cargo test -p marlin-gdrive` runs the tests of the Google Drive provider for mounts and of the saved Google sign-in. A plain `cargo test` does not include them. They run against a fake Drive server and a fake token endpoint inside the test process, with the in-memory keychain, and need no network and no account. See [Google Drive mount provider](mount-gdrive.md). **Never add `--ignored` or `--include-ignored` to this command.** `tests/live.rs` is a manual test that reads a real Google account. Its header has the command and the one environment variable.
- `cargo test -p marlin-sftp` runs the tests of the saved servers on the in-memory keychain, the host key rules, a connect to an SSH server inside the test process, and the mount provider. A plain `cargo test` does not include them. They need no network and no account. The provider's tests in `tests/provider.rs` start OpenSSH's `sshd` as the user on 127.0.0.1, so they need `/usr/sbin/sshd` and `ssh-keygen`: a Mac has both, and CI installs `openssh-server`. See [SFTP mount provider](mount-sftp.md#testing).
- `cargo test -p marlin-smb-client` runs the saved-server tests on the in-memory keychain, and the client and [SMB mount provider](mount-smb.md) tests against fake `marlin-smb` scripts, including a hung call whose child process dies with it, and a stopped call. They need no Samba, and `npm run test:rust` runs them. The tests that wait for a process to exit read its state with `ps`, which the `procps` package gives on Linux. A plain `cargo test` does not include them.
- `cargo test -p marlin-mount` runs the mount helper's tests. A plain `cargo test` does not include them. They talk to the helper over a real socket in a temporary folder, with a fake adapter. One test finds the helper with `pgrep` and `ps`: a Mac has them, and the `procps` package gives them on Linux. `tests/client.rs` tests the app's client the same way: it starts the built helper, and it stands in a fake helper where it needs another protocol version. `tests/gdrive.rs` runs the helper with its real Google Drive provider against a fake Google and the in-memory keychain. Its two tests that mount need FUSE: `test-in-docker.sh` runs them on Linux, and `test-on-mac.sh` runs them on a Mac. See [Mount helper](mount-helper.md).
- `src-tauri/crates/marlin-mount/test-sweep.sh` checks the helper against a real dead mount. It needs a Mac with macFUSE, or Linux with `fuse3`. No `cargo test` covers the real unmount of a dead mount, so run it when you change that code. See [Mount helper](mount-helper.md).
- `src-tauri/crates/marlin-fuse/test-in-docker.sh` runs the Linux mount adapter's tests in a container: unit tests, tests that mount an in-memory provider through FUSE and write through it, the helper's tests (two of them mount a Google account against a fake Google), and `test-sweep.sh`. The container installs `rsync` and `vim-tiny`. See [Linux mount adapter](mount-linux.md).
- `src-tauri/crates/marlin-fuse/test-on-mac.sh` runs the macOS mount adapter's tests on a Mac: the shared mount tests through macFUSE, write tests included, a Finder copy, the helper's tests, and `test-sweep.sh`. It needs macFUSE 5 with both switches on, and CI does not run it. On a Mac, a plain `cargo test -p marlin-fuse` runs only the unit tests of the macOS half. See [macOS mount adapter](mount-macos.md).
- `scripts/check-bundled-mount-helper.mjs` is not a `cargo test`. The release dry run in CI runs it on each built bundle: it starts the helper from the macOS app or the `deb` and checks that it answers. See [Mount helper](mount-helper.md#building-and-bundling).
- `scripts/check-linux-package-libraries.mjs` is not a `cargo test`. On Linux, the release and the release dry run extract the deb and the rpm the build made. The check fails when a program in `usr/bin` needs a library that neither the build machine nor the package's rpath folder holds. See [The libzpl library in the Linux packages](release-signing.md#the-libzpl-library-in-the-linux-packages).
- `scripts/check-bundled-licenses.mjs` is not a `cargo test`. The release and the release dry run run it on what the build made: the built `Marlin.app` on macOS, and each extracted package on Linux. The check fails when one of the six license files is missing or empty, or when `THIRD-PARTY-LICENSES.txt` lacks a section. See [Licenses](licenses.md#the-check-on-a-built-bundle).
- `cargo test -p marlin-smb` runs the SMB helper's tests. The tests start a Samba `smbd` (`marlin-test-samba`) as the user, on a free local port, with a temporary config in a short folder under `/tmp`. The server has one user in its own password file, a share the user may read, and one share the user may not. `Server::start` returns once `smbclient -L` names the share: smbd starts samba-dcerpcd at the first listing, and on a busy machine that can take half a minute and answer with no share. The tests cover `ping`, `read`, `space`, `read_directory` errors, and `list_shares` with the sign-in on stdin. They check the error code for a wrong password, a disabled account, a missing path, a refused share, file, or folder, a folder read as a file, a file listed as a folder, and a server that cannot be reached. A connection lost during a call has a unit test of its code only. `tests/provider.rs` runs the [SMB mount provider](mount-smb.md) against the same kind of server, with the in-memory keychain. The refused file and folder tests need a user other than root, because root reads any file. They run a native `smbd`, not a container, for four reasons: a Mac needs no Docker for them, the server starts in about a second, each test gets its own server, and `app-tests/sftp.test.ts` runs `sshd` the same way. A container would also need Docker inside the Linux test container. On a Mac the tests need Homebrew's `samba-dot-org-smbd`. Apple's `/usr/sbin/smbd` is a different server. `MARLIN_TEST_SMBD` and `MARLIN_TEST_PDBEDIT` point at other copies. On a Mac, `src-tauri/crates/marlin-smb/test-in-docker.sh` runs them on Linux. CI does not run these tests.
- A test that uses the keychain calls `marlin_test_keychain::install()` first. The `marlin-test-keychain` crate (`src-tauri/crates/marlin-test-keychain/`) is an in-memory keychain that takes the place of the real one. Tests link it: the app's unit tests and the tests of `marlin-gdrive`, `marlin-sftp`, `marlin-smb-client`, and `marlin-mount`. The one build that links it is the test build of the app (the `app-test` feature), for the [real-app tests](#real-app-tests). There is one for the whole test process, because the `keyring` crate holds one store per process. A unit test that reaches for the real Google accounts file gets an error, because reading that file can rewrite it.
- `src-tauri/tests/smb_integration.rs` holds manual tests that need a real SMB server. They are marked `#[ignore]`. The file's header lists the environment variables and the command to run them.
- `src-tauri/tests/gdrive_integration.rs` holds manual tests that call the live Drive API as the first account Marlin lists (the service account when `GOOGLE_SERVICE_ACCOUNT_KEY_FILE` is set). They are marked `#[ignore]`, and they read the real keychain. The file's header lists the command, the one environment variable, and what to do before the first run.

## What to test

- **A bug fix:** write the failing test first, then fix it.
- **Store logic:** a unit test.
- **A user flow in the UI:** an end-to-end test.
- **Rust logic:** a Rust unit test next to the code.
- **Rust and the frontend working together, or a real OS integration the page shows** (the folder watcher, a real listing, a file operation): a real-app test.
- **Native drag, the app menu, system dialogs, an actual remote server:** no automated suite covers them. Test them by hand in `npm run tauri dev` and say so in the PR.
