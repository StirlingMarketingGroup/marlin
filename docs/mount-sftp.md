# SFTP mount provider (`marlin-sftp`)

`SftpProvider` shows one saved SFTP server to the [mount core](mount-core.md) as a `Provider`. It reads and writes: `can_write` and `ids_are_paths` are true, so a mount of it takes writes and an item's id is its path. The [mount helper](mount-helper.md#providers) opens it as the provider `sftp`.

The same crate holds the saved servers, the host key check, and the connect that the app's `sftp://` view uses: see [Location providers](location-providers.md).

**Covers:** `src-tauri/crates/marlin-sftp/src/provider.rs`, `open_sftp_channel` in `src-tauri/crates/marlin-sftp/src/connect.rs`, `src-tauri/crates/marlin-sftp/tests/provider.rs`, `src-tauri/crates/marlin-test-sshd/`
**Checked against the code:** 2026-11-26

## What a mount shows

- **The top is `/`**, not the user's home folder. A server's useful folders are often outside home, and a mount's top cannot move. The app's `sftp://` view also starts at `/`.
- **An item's id is its absolute path.** So a rename that another client makes looks like one item removed and another added ([Mount core](mount-core.md#what-a-provider-implements)).
- **Names are the server's.** A listing holds files and folders only. It leaves out `.` and `..`, FIFOs, sockets, and devices, because a read of a FIFO would hang the server. It also leaves out every name that holds U+FFFD: russh-sftp 2.1.2 decodes names lossily, so a name that is not UTF-8 and a real name with U+FFFD could get one id (#637). It decodes the server's file handles the same way, so on a server whose handles are not UTF-8 every listing and read fails until #637.
- **Attributes:** a file's size, a folder's size of 0, and the modified time to the second. A file's revision is its size and its modified time, written `size:mtime`. SFTP gives only those two, and the time only to the second, so two changes within one second that leave the size the same look like no change. No file is marked read-only: the provider does not know that from the attributes.

## Links

The mount core knows files and folders only. A link shows as what it points to, under its own name and path:

| The link points to                                                              | The listing shows                                                                                                         |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| A file                                                                          | A file with the target's size and time.                                                                                   |
| A folder                                                                        | A folder, only when the listed folder was reached with no link on the way, and the target is not that folder or above it. |
| A missing target, a loop, or a target the server will not describe to this user | Nothing: the link is left out.                                                                                            |

"Reached with no link on the way" means the server's `realpath` of the listed folder is its id. So a walk crosses at most one folder link, and links that point into each other's folders cannot make an endless tree. On a Mac, for example, `/tmp` is a link to `/private/tmp`: it shows in `/`, but a link to a folder inside it does not show under `/tmp`. It shows under `/private/tmp`. The rule needs a server whose `realpath` follows links, as OpenSSH's does. On a server whose `realpath` only tidies the path, a link to a folder above it shows at every depth, until the path grows too long for the server.

`item` follows links whatever the listing showed.

## The calls

- **`item`** asks for the path's attributes, following links.
- **`list`** reads the folder, then looks up its links, at most 8 at once. OpenSSH answers "no such file" for a file it is asked to list, and other servers answer a generic "failure" for a file or a missing folder. So after either answer the provider asks what the path is. A file is `NotAFolder`, and the ask's own "no such file" or "permission denied" gives the error.
- **`read`** opens the file and asks for the range in pieces, at most 8 at once, in order. A piece is the largest read the server names in `limits@openssh.com`, up to 256 KiB, or 32 KiB from a server that names none. A server may answer a piece short. The piece then asks for only the bytes it still lacks, while the pieces after it go on. The end of the file, or an empty answer, ends a piece. Memory holds the asked range plus the pieces in flight. The file is never read whole. Each `read` opens and closes the file, which costs one more round trip per read. Nobody has measured what that does to a copy over a slow link.
- **`space`** asks `statvfs@openssh.com` about `/`. A server without that extension, or one that answers it with an error status, gets 1 PiB as both total and free: zero free would make file managers refuse to copy. The space is that of the disk that holds `/`, which can differ from the disk of a folder the user browses.
- **`MAX_CALLS` is 4.** The helper sets an SFTP mount's `max_calls` to it. The app downloads one file at a time per server, because some servers fail on parallel reads, and one read here already keeps 8 requests going. Nobody has measured how fast either number is.

## Changes and uploads

A name that is empty, `.`, `..`, or that holds `/`, a NUL, or U+FFFD is `NotSupported` before any request. A path built from the first of those would name another item, and a listing hides U+FFFD (#637), so a file made under one would vanish from the mount. `check_new_item` refuses the same names, so the core refuses a new file under one at once.

A change call (`create_folder`, `remove`, `rename`) asks its first question in a call of its own, which runs once more on a new connection when the old one died while idle: nothing has changed yet. The change itself, and everything after it, runs once: the server may have acted before a lost answer came back, so a lost connection is `Offline`. A byte call (`create_file`, `replace_bytes`) runs once too. The core tries a failed upload again by itself, after 5 seconds at first and up to 5 minutes. An upload the server refuses (`AccessDenied`, `NotSupported`) waits for an edit, a new modified time, a rename, or a retry the user asks for.

- **`create_folder`** asks what the parent is. A missing parent or a refusal is `NotFound` or `AccessDenied`. Anything that is not a folder is `NotAFolder`. It then makes the folder. OpenSSH answers a generic failure when the name is taken: a following lookup that finds the path is `Conflict`, one that finds nothing is `NotSupported`, and any other answer to it maps the same way as a read. `rename` and `create_file` read a generic failure the same way. The call returns the new folder.
- **`remove`** is `NotFound` when the item's path is not in the folder the core names. It looks the item up without following a link, then removes a folder with `rmdir` and anything else, including a link, with `remove`. A link is removed itself, never what it points to. A folder whose `rmdir` answers a generic failure is `NotEmpty` when the folder holds a name other than `.` and `..`, and `NotSupported` when it does not. One page of only `.` and `..` does not show that the folder is empty.
- **`rename`** without a replace sends SFTP's rename, which never overwrites. A generic failure is read as in `create_folder`; a folder moved into itself ends as `NotSupported`. With a replace, a replace item that is not in the destination folder is `NotFound`. Otherwise one `posix-rename@openssh.com` puts the item at the replaced path. A generic failure of it for a folder is read as in `remove`, so a folder to replace that holds anything is `NotEmpty`, and nothing changes. A server that does not offer that extension answers `NotSupported` after the two lookups, and no rename is sent. A server that advertises the extension and then refuses the request answers `AccessDenied`. By its version, OpenSSH's `sftp-server -P posix-rename` does that, or does not advertise the extension at all (OpenSSH 10.5 does not). The new path is the replaced item's path, which on a server whose disk ignores case can differ from the requested name only in case.
- **`create_file`** looks the name up first and answers `Conflict` when it is taken, before anything is sent. It writes the local file to `.marlin-{pid}-{nanos}-{n}` in the parent, then renames that file onto the name. SFTP's rename never overwrites, so a file that took the name in the meantime is `Conflict` and stays. The returned item uses the attributes read back before that rename. Nothing is asked after it.
- **`replace_bytes`** looks the item up without following a link. A link is replaced through the first name `realpath` returns, so the link stays and its target changes. Anything that is not a regular file is `NotSupported`, which also covers a link whose `realpath` only tidied the path and gave the link back, and a target whose name holds U+FFFD. A server without `posix-rename@openssh.com` gets `NotSupported` before anything is sent. A revision that is not the one the core sent is `Conflict`, and nothing is sent. The call then opens the file for writing and closes it at once: a refusal is `AccessDenied` before any byte goes out. The new bytes go to a `.marlin-` file in the target's folder, with mode `0600` while they upload. A second lookup whose revision changed during the upload is `Conflict`, and the temporary file is removed. That lookup, the file as it is now, also decides what the new file gets: its group, when the server gives it and it differs from the new file's, then its access bits (`0777` of its mode: a normal write clears set-user-ID and set-group-ID). So a mode or a group another client changed during the upload is kept. Both go through the open file, never by its name. A server that refuses the group refuses the replace: `AccessDenied`, and the old file stays, because the new file would let other people read it. The new file's owner is the signed-in user, as with an editor's safe save: only root may give a file away, and with the old group and access bits nobody can read it who could not read the old one. A link pointed elsewhere during the upload is `Conflict`. The returned item is built before the publish, so nothing is asked after it. The publish is one `posix-rename@openssh.com`, the same one a rename with a replace uses. The returned item keeps the id the core passed, so a link keeps the link's path and shows the new bytes.

An upload sends pieces of the server's `max_write_len` from `limits@openssh.com`, capped at 256 KiB, or 32 KiB when the server names none, at most 8 at a time. It sets the modified time, and the access time with it, because SFTP sets the two together. A server that refuses to set them keeps its own. When the server offers `fsync@openssh.com`, the upload asks for it before reading the attributes back; a server that then says the request is unsupported is ignored. A local file that cannot be read is `Other("the file to upload could not be read")`. The temporary name is removed when the call fails or the core drops it. When the connection is lost first, the provider keeps the name and removes the file at its next upload.

A server without `posix-rename@openssh.com`, or one that denies it, takes new files, folders, renames without a replace, and removes, but no replace. An upload it refuses waits for the user ([decision 0008](decisions/0008-read-only-files.md)).

### Known gaps

- A connection lost during an upload, after the temporary file's open answered, leaves a `.marlin-` file until the provider's next upload, and for good when the provider ends first. When the server makes the temporary file and the open's answer never arrives, no later upload removes it.
- A file in a folder where the signed-in user may not make files cannot be replaced through the mount (`AccessDenied`): the new bytes go to a temporary file beside it.
- A new file in such a folder is refused only at upload (#784). The mount shows it, and it stays on this computer as a refused unsent file.
- A listing taken during an upload shows its `.marlin-` file.
- A folder renamed while an upload into it runs keeps that upload's `.marlin-` file: the server moves it with the folder, and its removal looks for it under the old path.
- A move between two of the server's file systems is `NotSupported`, because SFTP's rename cannot cross them. Copy the item, then remove the old one.
- A final rename whose answer is lost leaves the file published while the core tries again, so a new file then gets `Conflict` on every try and a replaced file gets a conflict copy of its own bytes.
- Another client's change between the last revision check and the rename is overwritten, and SFTP keeps no older revision to recover it from.
- Two changes within one second that leave the size the same look like no change.
- A file whose group the signed-in user may not set cannot be replaced through the mount (`AccessDenied`). A replaced file that another user owned belongs to the signed-in user afterwards.
- A replaced file is a new file: a hard link to the old one keeps the old bytes, and an access control list beyond the mode is not copied.
- A link moved to a folder where its target does not resolve moves on the server, and the call answers `NotFound`. A link that does not resolve never shows in a listing.
- A link to a folder shows as a folder, so a recursive delete walks into it and removes what it points to, where a local `rm -r` removes only the link (#757).

## The account

`SftpAccount` is one account: a user on a saved server's host and port, with the sign-in attempts that failed. It holds no connection. A caller keeps one per account for its whole run, and builds each provider on it with `SftpProvider::new`. So what the server refused stays refused across mounts, and each mount's connection closes with its provider. The account tells its sign-ins apart by the password, the local key path with its passphrase, or the use of the SSH agent.

- **An agent sign-in reads `SSH_AUTH_SOCK`** from the process that connects. Without it, an agent server answers `SignInNeeded`.
- **The provider signs in as the account's user only.** When the saved server for the host and port now holds another user, the call is `SignInNeeded`, and no connection is opened.
- **One attempt at a time per account.** An attempt holds the account's lock from its check to the moment it records how it ended. An attempt outlives the call that started it (see [The connection](#the-connection)). Without the lock, a second mount could send a password while the server is still judging the first try of it.
- **Each attempt reads `sftp-servers.json` again, and the keychain for a password or a key's passphrase**, so a changed sign-in works with no unmount. Once the saved user matches the account, it reads `known_hosts` once and passes those keys to the handshake.
- **The account remembers each attempt the server refused, and each that failed before the server judged it**, with its sign-in.

| The attempt ended                                                                                                                                                  | The same attempt is made again                                                          |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| The server refused the password                                                                                                                                    | Never, while the `SftpAccount` lives. A new host key does not change that.              |
| The server refused the key, or every agent key                                                                                                                     | After `retry_after`.                                                                    |
| Before the server judged the sign-in: an unknown or changed host key, a key that needs its passphrase, a key file that does not load, or an agent that cannot sign | After `retry_after`, or at once when `known_hosts` holds other keys for the server now. |

- **Why a password is never sent again:** servers lock an account after a few wrong ones.
- **Why a refused key waits:** the fix is often on the server, as a key added to `authorized_keys`.
- **Why a failure before the sign-in waits:** a mount gets a provider call for every file the OS touches, and each call would open a connection that fails the same way. OpenSSH 9.8 and later penalize an address for such connections (`PerSourcePenalties`) and then refuse it for a while, which also blocks the user's own `ssh`. An agent that could not sign, as when the user declines its prompt, waits too: otherwise the prompt would come back with the next call.
- **A change is tried at once.** Another password, key path, or passphrase is a new sign-in. Trusting the server's key in the app changes `known_hosts`. A new key file under the same path waits out the old failure.
- **Not remembered:** a server that cannot be reached, a server that closes the connection during the sign-in (unless it already refused an earlier agent key), a password that gets no answer within the attempt's 60 seconds, and a server that signs in but does not start SFTP. The next call tries again.

## The connection

- **Each `SftpProvider` holds one connection**, opened by the first call that needs one and kept for the calls after it. Dropping the provider closes it once no call uses it.
- **An attempt to connect runs in a task of its own**, and every call that needs a connection meanwhile waits on it. The core cancels a call by dropping it. An attempt inside that call would end with it: a cancel during a keychain prompt would let the next call start a second prompt, and a cancel while the server judges a password would lose the refusal.
- **A connection that ends is seen at once.** The provider watches the read half of the SFTP channel. When it ends, every request still waiting ends too: russh-sftp itself would wait out its time limit.
- **A connection that ended is never used again.** A call that lost a connection that was there before the call runs once more on a new one. A read repeats, and so does the first request of a change, which has changed nothing. A byte call does not repeat. A second loss is `Offline`.
- **A connection that died silently**, as after a laptop sleeps, ends within 20 seconds. A task beside each connection asks the server every 5 seconds whether it is there, and ends the connection when the server has been quiet for 15 seconds: no answer to the ask, and no SFTP bytes since the ask or since the last bytes before it. Bytes count as an answer, because on a slow link the answer can queue behind file data already on its way. That is inside the core's 30-second call limit, so a call waiting on the dead connection loses it: a read, and the first lookup of a change, run again on a new one, and a change or an upload answers `Offline`.
- **An attempt has 60 seconds** from the TCP connect to the SFTP channel, then fails with `TimedOut`, so a connection that dies during the sign-in cannot hold every call. The keychain read before it has no limit, since its prompt waits for the user.
- **russh-sftp's own limit per request is 600 seconds.** It starts when a request is queued, and an upload keeps 8 writes queued, so on a slow uplink the last one waits its turn a long time. The core's limits decide instead: its 30-second call limit for a call, and its stall rule for an upload.
- **An open the core cancels before its answer** may leave a handle on the server that nothing can close. The provider then stops using that connection: it closes when the calls on it end, and a closed session frees all its handles. An upload waits for the close of its temporary file, and of a replace's write check, before it goes on. Every other handle is closed by a task of its own after the call.

## Errors

| What happens                                                                                                                                                     | The call returns                                                                                                                                                                                                           |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The saved server cannot be read, a password sign-in cannot read its password from the keychain, or a key needs a passphrase the keychain cannot give             | `SignInNeeded`                                                                                                                                                                                                             |
| The host key is not in `known_hosts`, or does not match the saved one                                                                                            | `SignInNeeded`. The app can trust an unknown key. A changed key has no override in the app.                                                                                                                                |
| The server refuses the sign-in, the key needs its passphrase, the key does not load, or the agent cannot sign                                                    | `SignInNeeded`                                                                                                                                                                                                             |
| The saved server holds another user than the account's, or the same attempt failed and must still wait ([The account](#the-account))                             | `SignInNeeded`, with no connection opened                                                                                                                                                                                  |
| The server cannot be reached, or closes the connection during the sign-in                                                                                        | `Offline`                                                                                                                                                                                                                  |
| The connection ends during a call                                                                                                                                | `Offline`. A read, and the first request of a change, run once more on a new connection when the connection was there before the call. A change whose answer is lost, and a byte call, are `Offline` and do not run again. |
| `known_hosts` cannot be read, the server refuses SFTP or does not answer the request for it within 10 seconds, or the SFTP channel does not start in another way | `Other("the SFTP connection could not start")`                                                                                                                                                                             |
| The server answers "no such file"                                                                                                                                | `NotFound`                                                                                                                                                                                                                 |
| The server answers "permission denied"                                                                                                                           | `AccessDenied`                                                                                                                                                                                                             |
| The server answers a generic failure to a write (OpenSSH does for a full disk or quota)                                                                          | `NoSpace`                                                                                                                                                                                                                  |
| The name is already taken, or the file's revision is not the one the caller sent                                                                                 | `Conflict`. Nothing is overwritten.                                                                                                                                                                                        |
| A folder to remove or replace holds anything                                                                                                                     | `NotEmpty`. Nothing inside it changes.                                                                                                                                                                                     |
| The server answers any other error status                                                                                                                        | `NotSupported`: a status is about one item                                                                                                                                                                                 |
| The server sends an answer the provider cannot read                                                                                                              | `Other("the SFTP server sent an answer Marlin could not read")`                                                                                                                                                            |
| A sign-in attempt passes its 60 seconds, or a request passes russh-sftp's 600 seconds                                                                            | `TimedOut`                                                                                                                                                                                                                 |

On macOS the connection first waits up to 20 seconds for a Local Network answer ([macOS Local Network access](location-providers.md#macos-local-network-access)), and it is still `Offline` when it gets none.

No `Other` text holds a path or a secret.

## Testing

`cargo test -p marlin-sftp` runs the tests, and `npm run test:rust` includes them. `tests/provider.rs` needs `/usr/sbin/sshd` and `ssh-keygen`: a Mac has both, and CI installs `openssh-server`.

- **Against OpenSSH:** each test starts `sshd` as the user on 127.0.0.1, with key sign-in only, as `app-tests/sftp.test.ts` does. A TCP relay sits between the provider and `sshd`, so a test can count connections, see which are still open, and cut them all at once. Both come from the test-only crate `marlin-test-sshd`. `Sshd::start_denying` starts the same server with `internal-sftp -P`, so OpenSSH refuses the named requests. The keys are an Ed25519 key, an RSA key, and a key the server does not accept. The tests cover listings, a FIFO, reads at an offset, the link rules with a walk that would never end without them, the errors, an RSA sign-in, unknown and changed host keys, a refused key and its wait, an unknown host key that opens one connection until `known_hosts` changes, a key file that does not load and its wait, an account for another user than the saved one, a dropped provider that closes its connection, a cut connection, and a connection that goes silent, which the relay keeps open and quiet. They also cover making, moving, and removing folders and files, an upload through a temporary name that keeps the old mode, a cut during an upload that leaves the old file whole, a server that denies `posix-rename` and so replaces nothing, and a change that runs once more only while its first request has changed nothing.
- **Against a server inside the test:** a russh server with password sign-in, whose SFTP server offers only `posix-rename@openssh.com`, and `statvfs@openssh.com` when a test asks, and answers one request at a time. It covers a refused password, also when the call that sent it was cancelled, and across two providers on one account, also when the second starts while the server still judges the first; an agent that cannot sign, free space from a server without `statvfs` or one that answers it with an error, reads that come back short, a path the user may not read, a generic failure to list, a connection lost during a call, an open cancelled before its answer, a `mkdir` that answers once that the connection was lost and is not sent again, and a link whose `realpath` gives the link back, which is not replaced.

**Checked against a real server** on 2026-11-24: a mount of the public demo server `test.rebex.net` (Rebex's own SFTP server) through the helper, in the `marlin-fuse` Docker container, with a password sign-in. It mounted in 1.1 seconds, listed a folder of 16 entries in 0.8 seconds, and read 15 files of 409 KB in all in 8.4 seconds, about half a second a file. The time goes to round trips: a lookup, an open, the reads, and a close for each file. The Rebex check covers reads. Writes are checked against OpenSSH in the tests, and against no other server.

Not tested: a sign-in with a real SSH agent (the helper's tests use a private `ssh-agent`), a slow link where file data holds up the answer to the provider's ask, and SFTP servers other than OpenSSH, Rebex's, and the one in the test.
