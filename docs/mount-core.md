# Mount core (`marlin-vfs`)

`marlin-vfs` is the layer between a storage provider and an OS mount adapter. An adapter asks it for nodes and bytes. It asks a provider for items. The [mount helper](mount-helper.md) builds one `Vfs` per mount. The [Linux mount adapter](mount-linux.md) and the [macOS mount adapter](mount-macos.md) serve it to the OS. The first real provider is the [Google Drive mount provider](mount-gdrive.md). The Windows adapter (#375) comes next. The core can make a folder, remove an item, and rename or move an item. It can create, write, cut, rename, and remove a file in the spool, and it uploads a spooled file after the last writer closes. Both adapters call the writes. For a mount whose provider can write, the helper opens the account's spool and runs the uploader: see [Unsent files](mount-helper.md#unsent-files). After a crash, the next mount of that spool folder uploads a file whose writers had closed, and uploads a file that was still open as a recovered copy.

**Covers:** `src-tauri/crates/marlin-vfs/`
**Checked against the code:** 2026-11-26

The design is in [decision 0001](decisions/0001-mount-architecture.md). [Decision 0002](decisions/0002-node-ids-follow-lookup-counts.md) sets how long a node ID lasts. [Decision 0005](decisions/0005-mount-writes.md) sets how a mount takes writes. [Decision 0008](decisions/0008-read-only-files.md) sets what a file the account may not change does.

## The parts

| File            | Holds                                                                                                          |
| --------------- | -------------------------------------------------------------------------------------------------------------- |
| `provider.rs`   | `Provider`, the trait a storage backend implements, keyed by the backend's own `ItemId`.                       |
| `vfs.rs`        | `Vfs`, what an adapter calls. It owns the node table, the open handles, and the provider answers it reuses.    |
| `vfs/upload.rs` | The upload queue, one try of one spool file, and the calls an owner uses to see and drop what is still unsent. |
| `vfs/record.rs` | The record beside each spool file, and how a mount puts a spool folder from an earlier run back to work.       |
| `names.rs`      | The rules that make the names in one folder unique and safe for the OS.                                        |
| `spool.rs`      | `Spool`, the folder a mount keeps changed bytes in, and the local file calls the core uses on it.              |
| `error.rs`      | `VfsError`, the one error type. Each adapter maps it to an `errno` or an `NTSTATUS`.                           |
| `memory.rs`     | `MemoryProvider`, a provider that lives in memory. Tests here and in later crates run on top of it.            |

The crate has no FUSE, WinFsp, or Tauri types. It depends on `tokio`, `async-trait`, `chrono`, `serde`, and `serde_json`. `serde` and `serde_json` are for the spool's records, and no public type uses them. On Unix it also depends on `rustix`, and on Windows on `windows-sys`, for the free-space call that sizes the spool.

## What a provider implements

Five read calls: `root`, `item`, `list`, `read` (a byte range), and `space`. A provider returns the names the remote uses and does not make them unique or safe. `can_write` says whether the provider has the three change calls and the two byte calls. It defaults to false. A provider that leaves those calls out leaves `can_write` at that default. A mount of a provider that answers false is read-only.

Three more calls are optional. `locate` takes the remote's public ID, such as the file ID in a Drive link, and returns the items from the top of the mount down to that item. `None` means the remote has the item but the mount shows it in no folder. A provider that cannot do this answers `NotSupported`. `reference` is the reverse and makes no remote call. `None` means the item has no public ID, such as the top of the mount or a folder only the mount shows. A provider that leaves `reference` out gives no item a public ID. `thumbnail` gives the remote's own picture of a file, with the longer side the caller asks for (the remote may send another size), and the file's own width and height when the remote knows them. `None` means the remote has no picture of it. A provider that leaves it out answers `None`. The core asks it only about a file, never a folder.

`ids_are_paths` says whether an item's id is its path: `/` for the folder at the top, and the folder's id joined to the item's name with `/` below that (`/{name}` in the top folder). It defaults to false. Google Drive leaves it false: its ids are not paths to the core. Only this mount's own changes depend on it. The [SFTP](mount-sftp.md) and [SMB](mount-smb.md) providers answer true.

Three change calls, each optional: `create_folder`, `remove`, and `rename`. A provider that leaves one out answers `ReadOnly` for it. The Google Drive, SFTP, and SMB providers have all three and both byte calls. `create_folder` and `rename` get remote names, so a name can hold `/` or be `..`. A remote that cannot hold such a name answers `NotSupported`.

- `remove` and `rename` get the folder the core believes the item is in. The core's listing can be a few seconds old, so a provider that can tell answers `NotFound` when the item is no longer there.
- `remove` refuses a folder that holds anything (`NotEmpty`). A remote that has a trash moves the item there.
- `rename` moves and renames in one call. It may get an item to replace. The provider swaps the two in one step when the remote can. When it cannot, it moves first and removes second, so a call that fails halfway never leaves the name with no item. A remote that has a trash moves the replaced item there.
- `rename` with nothing to replace never removes or overwrites another item. A remote that keeps one name per folder answers `Conflict` when the name is taken.
- `rename` returns the item as the remote now has it. The id may have changed.

A file has a revision. The provider changes it whenever the file's bytes change. A folder has none. A provider without the byte calls gives none.

A provider marks a file read-only (`read_only` in `Attributes`) when it knows that the account may not give the file new bytes. It leaves the mark false when it does not know. A folder is never marked (#639).

Two byte calls, each optional: `create_file` and `replace_bytes`. A provider that leaves one out answers `ReadOnly` for it. Neither call has a time limit of its own. Each reports progress with the bytes sent so far, from zero, at least every few seconds while bytes move. The core stops an upload when its byte count has not grown for `upload_stall`.

- `create_file` makes a new file from a local file, names it with a remote name, sets its modified time, and returns it. A remote that keeps one name per folder answers `Conflict` when the name is taken. It never overwrites another item.
- `replace_bytes` replaces one file's bytes from a local file and sets its modified time. The id stays the same. When the file's revision is not the one the core based the upload on, the call answers `Conflict` and changes nothing. A file that is gone is `NotFound`.
- The local file can change while the call reads it. The core then does not count that upload as sending the file's current bytes, and it sends them again.

When a file's bytes change, its modified time or its size must change too. An adapter may keep bytes it already read until one of the two changes, as the [Linux mount adapter](mount-linux.md) does.

The text of a `VfsError::Other` holds no secret and no file name. The mount helper logs it.

An `ItemId` should stay with an item when it is renamed or moved, and the core then keeps the item's node and open handles across the rename. Google's file ID survives a move. The Google Drive provider's `ItemId` also names the shared drive, so it changes when a file moves between drives. A provider that only has paths uses the path. For such a provider, a rename that another client makes looks like one item removed and another added. For this mount's own rename, see "A rename that changes the item's ID" below.

## What an adapter calls

| Call                                                    | What it does                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lookup(parent, name)`                                  | Finds a name in a folder and returns its node. Counts one lookup on that node.                                                                                                                                                                                                                                                                                              |
| `forget(node, lookups)`                                 | Gives lookups back. The adapter must call it for every lookup, or the node table grows.                                                                                                                                                                                                                                                                                     |
| `attributes(node)`                                      | Returns the kind, size, modified time, revision, and read-only mark. A spooled file answers from the spool, with no revision, and is never read-only. Anything else is the node's fresh answer or the provider.                                                                                                                                                             |
| `open_folder`, `read_folder`, `release`                 | Opens a folder handle and reads its frozen listing in pages. `open_folder` takes no listing, and asks the provider nothing.                                                                                                                                                                                                                                                 |
| `rewind_folder`                                         | Takes the folder's listing into an open handle and freezes it there. Both adapters call it for every `readdir` from offset 0: the first read, and each rewind.                                                                                                                                                                                                              |
| `open`, `read`, `release`                               | Opens a file and reads any byte range. A spooled file is read from the spool. Opening for write needs a spool and makes no provider call. It fails with `ReadOnly` when the mount has no spool, and with `AccessDenied` for a read-only file.                                                                                                                               |
| `create(parent, name, access)`                          | Makes a new empty file that is only in the spool, and opens it. A mount with no spool answers `ReadOnly`. A name that is taken is `Conflict`.                                                                                                                                                                                                                               |
| `write(handle, offset, data)`                           | Writes bytes into a spooled file. A handle that is not open for write is `AccessDenied`. So is the first write to a clean file that the provider now marks read-only. An empty write changes nothing.                                                                                                                                                                       |
| `truncate(node, size)`                                  | Cuts or grows a file. A mount with no spool answers `ReadOnly`, and a read-only file `AccessDenied`. Cutting a clean file to zero reads nothing from the provider.                                                                                                                                                                                                          |
| `set_modified(node, modified)`                          | Sets the modified time of a spooled file. The upload sends that time with the bytes. A clean or fetching file, and a folder, is left as it is: no provider call sets only a time, and fetching a whole file to send a time is not worth it.                                                                                                                                 |
| `create_folder(parent, name)`                           | Makes a folder and returns its node. Counts one lookup on that node. A name that is taken is `Conflict`.                                                                                                                                                                                                                                                                    |
| `remove(parent, name, kind)`                            | Removes a file (`unlink`) or an empty folder (`rmdir`). The wrong kind is `IsAFolder` or `NotAFolder`.                                                                                                                                                                                                                                                                      |
| `rename(parent, name, new_parent, new_name, if_exists)` | Renames or moves. When the new name is taken, `IfExists::Replace` replaces that item and `IfExists::Refuse` fails with `Conflict`. A folder never replaces a file, and a file never replaces a folder. When the source is a remote item, another remote item holding the destination name can cause `Conflict`. A new file renamed over a read-only file is `AccessDenied`. |
| `space()`                                               | Total and free bytes. Asks the provider only when the core holds no fresh answer.                                                                                                                                                                                                                                                                                           |
| `writable()`                                            | True when the provider's `can_write` is true and `take_writes` gave the mount a spool. Each adapter asks once, before it mounts, and mounts read-only when this is false.                                                                                                                                                                                                   |
| `refresh()`                                             | Drops the cached listings and makes every stored attributes and space answer stale.                                                                                                                                                                                                                                                                                         |
| `fsync(node)`                                           | Puts a spooled file's bytes and its record on the disk. A clean or fetching file, and a mount with no spool, has nothing waiting and returns. A node that is gone is `StaleHandle`.                                                                                                                                                                                         |

The mount's owner calls `take_writes(spool)` when it builds the `Vfs`, as it calls `watch_calls`. It returns a `Result`. It puts back to work what an earlier run left in the folder, and `unplaced_spool_files` lists the spool files it could not place. Without a spool, opening for write, `create`, `truncate`, and `set_modified` are `ReadOnly`. The owner spawns `run_uploads` once for a mount that has a spool, and aborts it to stop uploading. Nothing uploads while that task is not running. Aborting it stops every upload in flight, and the spool files stay. `unsent` lists the spool files that should still reach the remote. `retry_now` sends a failed or refused one now. `discard_unsent` drops a file's unsent bytes: an item goes back to the remote's bytes, and a new file loses its name and is never uploaded. The owner also calls `locate(reference)` and `identify(path)`. They are queries: they make no node and count no lookup. `locate` walks the chain the provider returned and takes each name from the core's own listing, with the same escaping and ` (2)` suffixes a lookup shows. When the listing the core holds does not have the item, it asks for that folder once. `identify` reads those listings while they are fresh, and asks for a folder's listing when it holds none, as a lookup does. A file that is only in the spool is `New`. `thumbnail(path, size)` reads a path as `identify` does. It asks the provider only when the remote has the file's current bytes. A folder is `NoPicture`. A file only in the spool, a file with bytes in the spool, and a file whose bytes a write is fetching are `NotEligible`, as [decision 0009](decisions/0009-window-on-mount-paths.md), choice 7, says. Neither asks the provider for a picture, though reading the path can list a folder, as a lookup does. The picture call has the call limit and the time limit of any call. The picture shows the bytes the remote had when the core asked, so a caller that keys it by the file's size and time reads those first.

## Rules the core keeps

- **Nodes.** The root is node 1. A node lives while the OS holds a lookup on it or a handle is open on it. A spooled item or new file also lives until its spool file goes. An open folder holds its own node and the node of every item in its listing. When nothing holds a node, the core drops it. An ID is never reused in a mount. A node that is gone gives `StaleHandle`.
- **Stable identity.** A node is tied to the provider's `ItemId`. On a provider whose ids stay with their items, an item the remote renamed or moved keeps its node and its open handles. On a provider whose ids are paths, only this mount's own rename keeps them: see "A rename that changes the item's ID".
- **Names.** `escape` turns each character the OS forbids into `%XX`, in upper-case hex, and the names `.` and `..` into `%2E` and `%2E%2E`. A `%` becomes `%25` only where the text after it would read as an escape. Every other `%` is kept, so `My%20File.pdf` shows as `My%20File.pdf`, and `%2f` is plain text. `unescape` gives every remote name back from its escaped form, and every name the OS can send maps to a remote name that escapes back to it. A test checks both over every name of up to seven characters from `%`, `2`, `5`, `E`, `F`, `/`, `.`, and `a`. A name that occurs once in a folder is kept. Items that share a name are taken in `ItemId` order: each keeps the name if it is still free, or gets the first free ` (2)`, ` (3)` before the extension. The mapping is worked out again for each listing and is not stored, so a suffix can change when a duplicate is added or removed.
- **Name rules per OS.** `NameRules` holds two functions: which characters are forbidden, and the key that decides whether two names are the same name. `POSIX` is the only rule set today. Windows reserved names come with the Windows adapter (#375). macOS mounts use `POSIX` until they get rules of their own (#542).
- **Limits.** Each mount runs at most `max_calls` provider calls at once (default 16). A call that does not finish within `call_timeout` (default 30 seconds), waiting included, fails with `TimedOut`. Dropping the future of a core call cancels its provider call. An upload's byte calls do not take one of those slots and have no call time limit. A conflict copy's `item` call, the remove of a stray item, and the check before an adopted file's first try are ordinary calls. At most `max_uploads` uploads run at once (default 4). A file waits `settle` (default 2 seconds) after its last writer closes, or after its last change, before it uploads. An upload whose progress has not moved for `upload_stall` (default 60 seconds) is stopped and fails with `TimedOut`.
- **Listing cache.** A folder's listing is reused for `listing_ttl` (default 5 seconds). The cache holds at most `max_listings` folders (default 64), and 0 turns it off. A listing that started before a `refresh()` is never put in the cache. On a provider whose ids are paths, removing or renaming an item, making a folder, and an upload that makes a file each drop the cached listings at and under the item's path.
- **Attributes.** A node keeps the provider's latest answer about its item. The answer comes from a listing, an `item` call, or a change the provider confirmed, an upload included. `attributes`, and the folder check in an `open` for read, reuse it for `attributes_ttl` (default 5 seconds), and 0 turns that off. An `open` for write uses the kind the node holds, however old. So a listing and then the attributes of each item in it cost one provider call. The answer goes away with its node, so the node table is the bound and there is no size option. `lookup` returns the latest answer the node holds, and so does each entry `rewind_folder` freezes. A stored size never limits a `read`. An `open` in that time does not notice that the remote removed the file.
- **Free space.** The core reuses the provider's answer for `space_ttl` (default 30 seconds), and 0 turns that off. A failed call is not kept. macOS asks for the free space at every open of a file ([macOS mount adapter](mount-macos.md#how-a-mount-behaves)).
- **Age and order.** A listing, an attributes answer, and a space answer are each fresh for their time limit from when the answer came. So a listing that took longer than `listing_ttl` is still reused. The core orders answers by when it asked: one asked for earlier never replaces one asked for later, however late it comes.
- **Changes run one at a time.** `create`, `create_folder`, `remove`, `rename`, and `discard_unsent` share one lock per mount, held from the first name lookup to the end of the change. An upload's confirm takes it too, and waits for it with no time limit. So two calls that make the same name cannot both succeed. A change that waits longer than `call_timeout` for the lock fails with `TimedOut`. Reads and listings never take the lock.
- **The core shows its own changes at once.** After the provider confirms a change, the core edits the listing it holds for each folder the change named, by item ID. It does not ask the provider again. A listing the core asked for before the change ended, and that answers after it, is not put in the cache.
- **A change with no clear answer drops the listing.** When a change call fails, runs out of time, or is cancelled, the remote may or may not have changed. The core drops the cached listing of each folder the call named, and the next lookup asks the provider.
- **Names a mount can make.** The provider gets `unescape` of the name the OS sent, and every name the OS can send maps back to itself. A suffix the mount added becomes part of the remote name when the item moves: moving `a (2).txt`, the second of two remote `a.txt`, to another folder names it `a (2).txt` on the remote. Renaming it in its own folder to `a (2).txt` changes nothing.
- **A rename that changes the item's ID.** On a provider whose ids are paths, a rename moves every node, new file, and place at or under the old path to the new path, so open handles and nodes inside a renamed folder keep working, and a process whose working folder is inside it does too. A path change stops a spooled file's upload that is still running and clears a refusal: the file is sent to the new path after the settle time. An upload that already landed is confirmed at the new path. The listings at and under both paths are dropped, and a listing in flight across the change is not kept. A call that waited on the provider while its node's path moved starts over at the new path, also when the provider answered with an error. A provider whose ids are not paths can still give one moved item a new id, as Google Drive does for a file moved between My Drive and a shared drive: the core moves that item's node to the new id.
- **A path names one node at a time.** On a provider whose ids are paths, a folder this mount makes, a file an upload makes, and the new path of a rename each take their path. The listings at and under that path are dropped. A node still at the path, or inside it, was left there by another client's change. A clean one is retired. A spooled one becomes a new file beside it, named `{stem} (conflict YYYY-MM-DD HH-MM-SS){extension}`, so its unsent bytes still upload, and never over the item now at the path. One whose name stays on this computer is retired like a clean one.
- **A rename onto a name that another item holds on the remote.** When the source is a remote item, a rename fails with `Conflict` when an item in the destination, other than the one it moves and the one it replaces, has the new name on the remote: which of the two items then shows under the name would depend on their IDs. So in a folder with two remote `a.txt`, shown as `a.txt` and `a (2).txt`, renaming `a (2).txt` onto `a.txt` replaces the first and leaves one `a.txt`, and renaming another file onto `a (2).txt` replaces the second. With three remote `a.txt`, renaming `a (3).txt` onto `a.txt` fails. The check runs on the listing the core holds: a duplicate that another client adds later can still take the name at the next listing.
- **A removed item's node** lives while a lookup or an open handle holds it. On a provider whose ids stay with their items, calls on a clean removed file get whatever the provider answers for that id. On a provider whose ids are paths, the node keeps no id, because the path can name another file now: `attributes` still gives a fresh answer the node holds, and every call that would ask the provider is `StaleHandle` (`ESTALE`). A spooled one keeps its own bytes either way.
- **The write spool.** A file's bytes are clean, being fetched, or in the spool. Clean and fetching reads ask the provider. Once the file is in the spool, every read, the size, and the modified time come from the spool file. The first write copies the remote file into the spool in pieces of 4 MiB, then applies the write. A first truncate copies only the bytes it keeps, so a cut to zero copies nothing. Opening a file for write does not ask the provider and does not copy it. The size a spooled file shows is its length on the disk: room a write has reserved shows once the write lands.
- **New files.** Creating a file checks its name against the folder listing, then makes the file in the spool, with no change call. The mount lists it from the spool, over the remote listing. When another client adds an item with the same name, the new file keeps its name and the remote item gets the next free numbered suffix. Removing a folder that holds a new file, or replacing it by a rename, fails with `NotEmpty`.
- **A new file renamed over a file.** The new file takes the old item's id: its bytes become the item's next bytes, and the new file never reaches the remote as its own item. One name is left, on the new file's node, which is what the OS already believes after a rename. The old item's node is retired. A spooled handle on it reads its own bytes. On a provider whose ids stay with their items, a clean handle on it reads the item by id, so it reads the new bytes once they upload. On a provider whose ids are paths, a clean handle on it is `StaleHandle` at once. When the newest answer the core holds marks the old item read-only, the rename fails with `AccessDenied`, and nothing changes. That answer also gives the upload its revision.
- **Read-only files.** The core refuses with `AccessDenied` what would put bytes in the spool for a read-only file: opening it for write, cutting it, and renaming a new file over it. It decides from the answer the node holds, however old, as it does for the kind, and asks the provider nothing. The first write to a file that is still clean also fails when the answer it fetches, or holds fresh, marks the file read-only: an app may have opened the file before the remote marked it. A file whose bytes are already in the spool is not read-only. Name changes still go to the provider: the core does not check the mark for them ([decision 0008](decisions/0008-read-only-files.md)).
- **A removed spooled file.** A handle that is still open keeps working. It reads, writes, and cuts the spool file. The file is no longer listed, its bytes are never uploaded, and the spool file is deleted when the node goes away.
- **The spool's limit.** The default limit is 10 GiB, or half the free space on the disk that holds the spool, whichever is smaller. The free space is measured once, when the limit is chosen. A write that would pass the limit waits for room, up to the call time limit, then fails with `NoSpace`. The bytes written before are kept. One file larger than the limit cannot be written, and a first edit fails before it downloads anything when the file it would leave, by a fresh stored size or by the edit's own end, is larger than the limit. A write past the size of the whole spool fails at once. An edit that adds no bytes never waits: after a remount, the files from the earlier run can hold more than a smaller new limit, and a cut must still free room.
- **Names that stay on this computer.** `stays_local` names the files a mount keeps locally. `finder_files` is the macOS set: `.DS_Store` and `._name`. `marlin_fuse::stays_local` is the set for the OS the adapter is built for, for the helper to pass. A file under one of those names is spooled and shown like any other, and never uploaded, whether it is new or already on the remote. The name used is the one the mount last showed. When the mount is dropped, it deletes the spool files that stay local, and keeps the ones that still have to upload.
- **One edit at a time per file.** Each spool file has a lock that a write or a truncate holds from its room check to the end of its disk call. Each disk call opens the spool file and closes it again, so a copy of many small files does not hold one open file each. A first edit that fails or is cancelled leaves the file clean, and the next read asks the provider.
- **Uploads.** One file has one attempt at a time, and that attempt stays until its answer has been applied, so a second try cannot start while the first one's answer is still landing. An edit that is still on the disk holds the file back. A write, a truncate, or a new modified time stops an upload that is running. The file is sent again after the next last close, or after the settle time when a truncate has no open handle. Opening a file for write does not stop an upload. The open writer holds the next try back until it closes and the settle time passes, including a writer opened during a failed try's wait. Renaming a new file stops its upload, and the next try uses the new name. Renaming an item whose id stays does not stop its upload, because the replace goes by id, and the uploader looks at the file again: a new name can move it into or out of the names that stay local. A rename that moves a path stops that file's upload, and the next try sends to the new path. Removing a file stops its upload. A removed item is removed by the `remove` call. When that call fails, the file is tried again after the call time limit, unless its upload is refused. A new file removed or renamed after its create answered, and before the core applied that answer, has its new remote item removed again.
- **A conflict, a gone file, and a missing revision.** When the remote's revision is not the one the upload was based on, the remote file is left as it is. The local bytes go into a new file in the same folder, named `{stem} (conflict YYYY-MM-DD HH-MM-SS){extension}`, as in `report (conflict 2026-11-19 14-03-27).docx`. The time has no colon. The node then shows the remote's bytes. A file the remote deleted is created again under its current name, and the node keeps that new id. An item with no revision fails the upload with `NotSupported`, so the upload is refused, and the item is never overwritten.
- **Retries.** A try that fails for a reason that can pass waits 5 seconds, then twice as long each time, up to 5 minutes. An edit starts the count again. A writer that closes during the wait, or a rename, sends the file after the settle time instead of the rest of the wait. Such a file is retried for as long as the uploader runs.
- **A refused upload.** A try that fails with `AccessDenied` or `NotSupported` is not tried again by itself, and `unsent` shows the file as `Refused`. An edit, a new modified time, a rename, and `retry_now` start a new try. A close with no edit does not. The refusal is not in the spool's record, so the next mount tries the file once again.
- **When a spool file is deleted.** A confirmed upload deletes the spool file only when that upload sent the bytes the file holds now. A later edit keeps the spool file, and the next replace is based on the revision the upload just stored, so the upload does not look like a conflict with itself. The same rule deletes the spool file after a conflict copy. The node then shows the remote's bytes.
- **The revision an upload is based on.** A fetch that copies bytes bases the spool file on the revision of the bytes it copies. It uses the answer the node holds while that answer is fresh, and it asks for the item before it reads when the answer is stale. A revision taken before the read can only cause a needless conflict copy. A fetch that copies nothing uses the revision the node holds, however old. A new file has no base revision. A new file renamed over an item takes the latest revision the core holds for that item: its node's answer, or the listing's when that is newer.
- **A create the node no longer wants.** The confirm takes the changes lock, then the state lock. A name change takes those locks in that order too, so the two cannot split one new file into an item under each other. When the node was removed, renamed, or replaced while the create ran, the new remote item is removed. If that remove fails, the item stays on the remote and shows in a later listing.
- **Spool records.** Each spool file has a record beside it, `{n}.record`. It says what the file is for: the item, or the new file's folder and name; the revision the bytes were based on; whether a try may have reached the remote; and, once every writer has closed, the file's length and modified time on the disk. The core writes it when that changes. The write runs under the state lock and is not synced. `fsync` puts the spool file and the record on the disk. The last close writes the record at once and leaves the sync to a background thread, so the adapter's thread never waits for the disk to flush. Each upload try syncs too, before its first byte call, so the record that says a try may have reached the remote is on the disk first.
- **A spool from an earlier run.** `take_writes` reads the folder. It deletes a half-written record, and a record whose spool file is gone. A spool file with no readable record is kept, counted against the spool's limit, and listed by `unplaced_spool_files`. It is never uploaded. A file that sends nothing, and a file whose name stays on this computer, are deleted. A file whose writers had closed, and whose length and modified time on the disk still match the record, is queued as it was. Anything else may be half an edit. It is queued as a new file named `{stem} (recovered YYYY-MM-DD HH-MM-SS){extension}`, in the same folder, and never over the original.
- **The check before an adopted file's first try.** A crash between a byte call landing and the confirm leaves a record that still says to send the file. The first try of an adopted file that a try may have sent looks at the remote first, and sends nothing when the bytes are already there. A new file is matched by name, size, modified time to the second, and the bytes, using the folder's cached listing. A replace asks for the item by id: an unchanged revision means nothing landed, and a changed one is matched by size, modified time, and bytes. When the item holds other bytes, the check looks for a conflict copy of the file in the folder, and when the item is gone, for a file under its name. A file no try ever touched is not checked, so another client's file is not taken for this one. This check is the fallback in decision 0005's risk 8. The Google Drive provider creates a file under a pre-asked id inside one call. Keeping that id across calls, which would replace this check for a new file, is #632.
- **Locking.** All state is behind one mutex that is never held across a provider call. Three spool file calls run under the state lock, and every other one runs in `spawn_blocking`, outside it. Deleting a spool file: whatever drops the last use of it does that under the lock, so the bytes are gone when it returns: `release`, `forget`, `remove`, `rename`, a confirmed upload, a conflict copy, `discard_unsent`, a first edit that fails, and dropping the mount. Building a record reads the spool file's length and modified time, and writing it is a few hundred bytes with no fsync, so the record stays in the order of the state changes. `take_writes` reads the whole spool folder under the lock too, before any other call can run. The lock that makes changes run one at a time is a separate one, and it is held across a change's provider call. A confirm, a conflict copy, and `discard_unsent` take that lock before the state lock. A fetch holds a per-file lock across its provider reads. Only another write or truncate of that file waits on it. Each spool file's edit lock is held across a disk call, and never while the edit waits for room.
- **Call results.** `Vfs::watch_calls` gives a mount's owner the result of every provider call, including the core's own `TimedOut`. A cancelled call, a cached listing, attributes a node already holds, and a space answer the core already holds report nothing. An upload's byte call reports like any other call, and an upload the core stops reports nothing. The mount helper builds a mount's health on it ([Health](mount-helper.md#health)).

Every mount uses the nine defaults. [Google's limits](mount-gdrive.md#googles-limits) says how the call limit and the call time limit fit the Drive API. Nobody has measured any of them against a real account.

## Known gaps

A listing the core asked for before an upload's confirm, and that answers after it, can miss a new file for that one lookup. It happens when the core holds no cached listing of the folder. That is the same window as risk 3 of [decision 0005](decisions/0005-mount-writes.md).

The remote can briefly hold bytes from the middle of an edit. It happens when an upload read the spool file during a write. The next upload sends the bytes the file holds after the edit.

A create stopped before it answers can still land on the remote. A new file removed or renamed during its create then stays on the remote under its old name, and shows in a later listing. The core cannot remove it, because only the provider knows the id it was created under (#632).

A replace the core stopped, one that ended on the stall rule, or one that lost its connection after its last byte went out, can still land on the remote. The next replace then finds a changed revision. The local bytes go into a conflict copy, and the file shows the bytes that landed.

A reopened file whose record still says closed relies on the length and the modified time on the disk to show that it changed. A power loss can keep an overwrite's new bytes and lose the new modified time. Linux also stamps that time from a clock that moves every few milliseconds, so a same-length write within one tick looks unchanged. In both cases the next mount sends the half edit over the original. A record still says closed only when its write at the reopen failed, or a power loss undid it. Only an fsync at every reopen would close the gap, and the core does not pay for one.

A listing that answers while a create runs, and that already holds the new remote item, shows it beside the new file with a numbered suffix, until the create's answer is applied.

On a provider whose ids are paths, the core cannot tell an item another client removed or moved and then made again under the same path from the item it held. A node that still holds the path, through a lookup the OS keeps or an open handle, serves the new item until this mount gives the path to another node. A cached listing of the path serves it for up to `listing_ttl`.

A replace that a rename of the same file stops may already be on its way. On a provider whose ids are paths it may then land under the old name as a second file.

## Testing

`cd src-tauri && cargo test -p marlin-vfs` runs the name tests and the conformance tests in `tests/conformance.rs`. They need no kernel driver, no network, and no account. Tests that depend on time run on tokio's paused clock. A wait for an upload also gives the blocking sync a millisecond at a time, and that wait does not move the clock. Tests that write use a temporary spool folder. `MemoryProvider` implements the three change calls and the two byte calls, and gives each file a revision. Its `write`, `remote_rename`, and `remote_remove` change the tree behind the mount's back, as another user of the remote would. `contents` and `largest_read` check that a write did not change the remote, and that a fetch reads it in pieces. An upload test starts `run_uploads` itself. `set_upload_delay` holds the byte calls, which change the tree only when the delay ends, so a stopped upload leaves the remote as it was. Halfway through the delay a byte call reports half the file as sent. `lose_upload_answers` makes a byte call change the tree and then never answer, as an upload whose answer a crash lost. `hide_revisions` makes `item` and `list` give no revision. `set_read_only` marks an item read-only, and `replace_bytes` of it then answers `AccessDenied`. `set_thumbnail` gives an item the picture `thumbnail` answers. `uploads` counts the byte calls. `MemoryProvider::with_path_ids()` gives a provider whose ids are paths.
